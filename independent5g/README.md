# Независимая проверка моделей на развёртываниях Open5GS

Протокол подготовлен 30.10.2026. Фактическое выполнение подтверждается журналом GitHub Actions
и сохранёнными артефактами. Локально пройдены 32 автоматические проверки. Их контрольные примеры
не являются данными эксперимента и не используются для научных выводов.

## Проверяемый вопрос

Сохраняются ли результаты сравнения пяти моделей при переходе к новым процессам,
идентификаторам экземпляров и ключам? Даёт ли добавление доступных результатов проверки
свидетельств преимущество перед метаданными при сопоставимой фактической частоте ложных тревог?
Положительный результат для сложной модели не является условием успешного выполнения задания.

## Заранее закреплённый протокол

1. Девять новых развёртываний: 601–603 — обучение, 604–606 — калибровка, 607–609 — окончательная проверка.
   Каждое собирается отдельным заданием GitHub Actions. Ключи и процессы создаются заново;
   пересечение исходных UUID и повторение файлов наблюдений запрещены проверками.
2. В каждой тройке периоды опроса составляют 0,2; 0,4; 0,8 с. Это изменение измерительной
   нагрузки. Абонентская нагрузка и состав типов функций в данном опыте не варьируются.
3. Только штатные обращения чтения к локальным NRF, AUSF, NSSF. Управляемые воздействия:
   остановка и приостановка процесса AUSF или NSSF с последующим восстановлением.
   Калибровочные развёртывания работают без воздействий.
4. Пять прежних архитектур: временная графовая сеть (TGN), графовая сеть GraphSAGE (GNN),
   сеть долгой краткосрочной памяти (LSTM), трансформер (Transformer), гистограммный
   градиентный бустинг (HGB). Дополнительный ориентир — прямое правило доступности транспорта.
5. Три состава входа: метаданные; метаданные и метод/ресурс обращения; те же сведения
   с доступными состояниями проверки контрольных единиц и независимого свидетельства.
   UUID, этап опыта, номер развёртывания, абсолютное время, метки и содержимое сообщений
   во входной вектор не включаются.
6. Масштабирование признаков определяется только штатными обучающими наблюдениями.
   История сохраняется внутри развёртывания и сбрасывается между развёртываниями.
   Восстановление и наблюдения нецелевой функции во время отказа входят в историю,
   но исключаются из функции потерь и основных показателей.
7. По три начальные инициализации на каждое сочетание: всего 45 обучений.
   Для всех моделей порог равен верхнему эмпирическому квантилю 0,99 штатных калибровочных
   оценок. Тревога определяется строгим превышением порога. Порог, параметры нормирования,
   состояние обучения и хеши данных записываются в `frozen-before-test.json` до расчёта
   итоговых проверочных оценок. Настройка по проверочным результатам отсутствует.
8. Метки отказа определяются журналом локального контроллера, а не решением проверяющего
   компонента. Пропуски, истинные и ложные тревоги считаются отдельно по развёртываниям.

## Показатели и ограничения вывода

Полнота по наблюдениям и эпизодам; фактическая доля ложных тревог; число отмеченных наблюдений
и число последовательных эпизодов ложной тревоги в час штатной работы. Экспозиция берётся
из монотонных часов реально записанных штатных интервалов, без удвоения времени из-за двух
наблюдаемых функций. Сохраняются также оценки моделей для каждого наблюдения и задержки
до первого отмеченного наблюдения. Последние не включают накопление пакета входных данных
и вычислительную задержку, поэтому не являются оценкой задержки эксплуатационного обнаружения.

Доверительные интервалы и парные разности вычисляются повторной выборкой целых проверочных
развёртываний; одинаковые индексы используются для сравниваемых методов. Инициализации
усредняются отдельно и не увеличивают число независимых развёртываний. Три развёртывания
дают только исследовательскую оценку неопределённости. Поправка на множественные сравнения
не применяется; объявлять статистически доказанное превосходство на этой основе нельзя.
Одинаковая калибровочная цель не гарантирует одинаковую частоту ложных тревог на проверке.

**Это опыт с отказами доступности. Он не проверяет семантические атаки, иной состав сетевых
функций, пользовательскую нагрузку или работу на операторской сети.** Метод и ресурсы
обращений фиксированы процедурами чтения, поэтому разнообразие интерфейсных признаков
ограничено. Используется существующий программный сборщик свидетельств с его ограничениями
доверия и жизненного цикла; аппаратная аттестация не заявляется.

## Файлы запуска и результаты

Задание: `.github/workflows/independent-deployment-ml.yml`.
Порядок: проверки → 9 сборов → 5 заданий обучения → единый отчёт.
Требуется дерево репозитория с существующими `cu5g`, `fullsuite`, `live5g`, `hybrid`,
`semantic5g`, `neural5g`; новая ветвь по умолчанию `codex/independent-deployment-ml`.
Базовая версия: `77d9b601feba35619e890d78e13e82357e9bcff3`; наличие перечисленных
каталогов в этой версии проверено на публичной странице GitHub. Ветка `main` содержит
только начальную запись репозитория и не подходит в качестве базы данного опыта.
При загрузке через API файл задания следует добавить последним, чтобы не запустить сбор
на частично загруженном коде. Перезапуск доступен через ручной запуск рабочего процесса
(workflow_dispatch) на этой ветви. Исходный коммит и хеши файлов закрепляются первым заданием.

Ожидаемые артефакты:

- `independent-registered`: протокол, версия кода, хеши и результаты проверок;
- `independent-native-601` … `independent-native-609`: новые наблюдения и журналы;
- `independent-model-*`: веса, пороги, оценки и показатели каждого обучения;
- `independent-final-report`: таблица показателей, парные разности и текст отчёта.

Приватные ключи и ключи аутентификации не входят в загружаемые артефакты.
Наблюдаемые сетевые назначения ограничены изолированной сетью контейнера ядра.
Оригинальные реализации моделей и проверяющего компонента не изменяются.
